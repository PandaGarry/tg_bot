> Продукт: **The Dead Lords (TDL) / «Мёртвые лорды»** — оригинальная undead-fantasy многопользовательская стратегия 4X.

## 1. Цель и принципы

Построить поддерживаемую, безопасную, расширяемую и визуально цельную 4X-стратегию с:
- собственным миром нежити, лордами, фракциями, существами, историей и визуальным языком;
- развитием поселения, зданиями, ресурсами, производством, исследованиями и очередями;
- глобальной картой, территориями, узлами ресурсов, маршами и разведкой;
- героями/командирами, армиями, PvE, PvP и воспроизводимыми отчётами боёв;
- кланами/альянсами, совместными целями, чатами и событиями;
- долгосрочной экономикой, сезонами, прогрессом и честной монетизацией;
- удобным touch-first интерфейсом на телефонах и полноценной компоновкой для широких экранов.

### Непереговорные инженерные принципы

1. Сервер и БД — источник истины для ресурсов, времени, боя, владения, платежей и результатов команд.
2. Любое действие игрока валидируется на сервере; клиент не может назначить себе ресурсы, уровень, награду или результат боя.
3. Изменения экономики и владения атомарны, идемпотентны и защищены от гонок.
4. Состояние мира переживает рестарт; таймеры и расписания не зависят от часов устройства.
5. Мировая изоляция обязательна на уровне сессии, actor, запросов, команд, БД и админских операций.
6. Сначала тестируемые доменные правила и данные, затем интерфейс и визуальные эффекты.
7. Не добавлять зависимости и не менять архитектурные границы без оценки пользы, стоимости и рисков.
8. Сохранять историю и обратимость: не запускать разрушительные миграции и массовые сбросы без резервной копии, теста восстановления и явного релизного допуска.
9. Доступность, локализация ru/en, адаптивность, производительность и безопасность — критерии готовности, а не «полировка потом».
10. Не копировать Viking Rise: используем только жанровые ориентиры, создаём собственную реализацию.

## 3. Оценка текущего технологического стека

| Слой | Сейчас в репозитории | Предварительная оценка |
|---|---|---|
| Язык и структура | TypeScript, pnpm workspace, Turborepo | Хорошая база для общего контракта и разделения доменов; нужны строгие границы пакетов и контроль циклических зависимостей |
| Runtime | Node.js; root требует Node >=22.12, CI использует Node 24 | Подходит для текущего сервера; зафиксировать и проверять одинаковую версию в CI и production |
| Клиентский UI | React 19 + Tailwind CSS 4 + Vite 8 | Современная основа для HUD/панелей; следить за размером бандла, доступностью и не переносить игровую симуляцию в React |
| 2D-сцена | PixiJS 8 | Разумный выбор для изометрического 2D мира и карты; WebGL fallback, управление памятью, batching, atlas и мобильный GPU — обязательные проверки |
| Сеть | WebSocket (`ws`) + Zod-схемы протокола | Подходит для realtime; требуется проверка авторизации, backpressure, версий, reconnect, команд и пространственной рассылки |
| Сервер | Node.js, собственное ядро модулей | Потенциально сильная доменная архитектура; главные риски сейчас — транзакции, гонки, миграции, изоляция миров и отказоустойчивость pump |
| БД | PostgreSQL + Drizzle | Хороший выбор; нужны уникальные ограничения, индексы, транзакционные инварианты, миграции и проверенное восстановление |
| Валидация | Zod 4 | Полезно для входных сообщений и команд; схемы должны совпадать с реальными доменными ограничениями, а не только типами |
| Тесты | Vitest 5, PostgreSQL для интеграционных тестов | Есть тестовая основа; требуется гарантировать ненулевой код при любом провале и запускать полный набор в CI |
| Нативные приложения | В текущем дереве не подтверждены | Не обещать App Store/Google Play на основании мобильного веб-интерфейса. Сначала адаптивный web/PWA, затем отдельное решение о Capacitor/нативной оболочке |

### Вывод по стеку

**Срочно менять стек целиком оснований нет.** TypeScript + React + PixiJS + Node.js + PostgreSQL — рациональная основа для браузерной многопользовательской стратегии. Сейчас приоритетнее исправить корректность серверного ядра и границы безопасности, чем устраивать рискованную массовую миграцию библиотек.

Отдельный этап технологической проверки должен:
- сверить версии и peer dependencies по lockfile, проверить advisories и лицензии;
- измерить production bundle, загрузку ассетов, FPS, GPU/CPU, память и сетевой трафик на слабых телефонах;
- проверить PixiJS renderer/fallback на iOS Safari, Android Chrome/WebView и desktop;
- проверить React render churn, долгоживущие подписки и утечки listeners;
- оценить горизонтальное масштабирование Node/Postgres, пул соединений и backpressure;
- принимать обновление major-зависимости только с тестом совместимости и измеримым выигрышем.

Не обновлять зависимости «до последних» без проверки release notes, CVE, breaking changes и совместимости с Node 24.

### Проверка конкретных версий (08.11.2026)

- Node.js: CI использует Node 24; root требует Node >=22.12. Зафиксировать Node 24 как production runtime. После стабилизации добавить Node 26 отдельной CI-матрицей и проверить нативные модули и PostgreSQL-драйвер.
- React 19.3.0 и PixiJS 8.22.0 соответствуют актуальным стабильным версиям на дату проверки; менять их сейчас оснований нет.
- Vite в lockfile обновлён до 8.3.6; Zod — до 4.6.7, `source-map-js` — до 1.2.2. Полный CI проходит; `pnpm audit --audit-level high` не находит High, но остаются 3 Moderate advisories для отдельной проверки.
- TypeScript в lockfile — 5.9.3; актуальная major-линия уже 7.0.2. Не делать слепой major bump: сначала отдельная проверка TypeScript 7 с tsconfig, Vitest, Zod, Vite plugins и всеми workspace-пакетами; при несовместимости рассмотреть промежуточную миграцию.
- Первый CI прогон выдал предупреждение о Node 20 в GitHub Actions v4. Workflow обновляется на Node 24-compatible major versions; обязательный CI включает `pnpm audit --audit-level high`.

### Состояние интерфейса и визуальной части

Текущий UI — **рабочий прототип, не production-ready игра**:
- React/Tailwind оболочка, экраны входа/регистрации/создания лорда и PixiJS-сцена уже существуют.
- В HUD обнаружены демонстрационные/неподключённые значения: VIP 1, уровень 1, сила 0 и нулевые ресурсы при отсутствии серверных данных. Часть вкладок показывает «Скоро»; Google/Yandex login — пока заглушки. Не выдавать эти элементы за готовые системы.
- Векторные заглушки зданий и текущая сцена не заменяют оригинальные игровые ассеты, анимации, состояния выбора/строительства и окружение.
- Полный 4X gameplay (глобальная карта, марши, армия, бой, командиры, кланы, исследования, события) пока не реализован в полном объёме. Экранные кнопки не являются доказательством серверной функциональности.
- Production build показывает главный JS chunk около 734.64 kB minified / 213.55 kB gzip и предупреждение о чанках больше 500 kB. Нужны lazy imports для Pixi/экранов, анализ состава бандла и измерения на слабых мобильных устройствах.
- Приоритет UI: убрать фиктивные значения или маркировать их как preview; показывать только подтверждённые сервером данные; реализовать loading/error/offline/reconnect states; затем единый оригинальный gothic-undead дизайн, безопасные зоны, touch targets, keyboard/focus, reduced motion и RU/EN.

- **AUD-005** — `/api/kernel/rejections` закрыт операторским токеном; HTTP-регрессия 403 без токена / 200 с токеном проходит CI.

- **AUD-022** — исправлено в приложении и БД: `createLord` сериализует создание через транзакционный advisory lock; уникальный индекс `(world_id, account_id)` защищает инвариант на уровне PostgreSQL. Конкурентный тест проходит CI run #75.
- **AUD-030** — частично закрыто: kernel и module migrations используют общий advisory lock key, версия модуля читается под lock. Блокировка всё ещё освобождается между этапами полного bootstrap; следующий шаг — один lock на весь startup migration sequence и тест смешанного rolling deploy.

## 5. Пошаговый план реализации

### Фаза 0. Синхронизация и baseline

**Цель:** установить единую актуальную копию и воспроизводимый запуск.
1. Сверить GitHub main, рабочую ветку и PR #9; сохранить историю и не перезаписывать неизвестные коммиты.
2. Разобрать открытые PR и историю веток; определить единственный активный поток.
3. Зафиксировать Node/pnpm/Postgres, env vars, запуск сервера, команды проверок и baseline commit.
4. Запустить `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm check`, `pnpm build`; сохранить логи и причины падений.
5. Проверить, что тесты не затрагивают базу `tdl`, а только отдельные `tdl_test_*`.

**Готово, когда:** рабочая копия и ветка согласованы; известен фактический baseline; все тесты либо зелёные, либо заведены точные блокирующие дефекты; пользовательские файлы не потеряны.

### Фаза 1. Защита данных и сессий (P0)

Миграции, multi-world isolation, сессии, logout, writer/pump, админские ручки, production config, резервное копирование. Сначала regression tests на отдельной БД и сценарии двух миров, затем исправления и повторные тесты.

**Готово, когда:** тесты на cross-world access, параллельные запросы, отказ БД, отзыв сессии и безопасное восстановление проходят; destructive migration не может сбросить данные другого мира.

### Фаза 2. Надёжность игрового ядра и экономики (P1)

Склад/производство, стартовый набор, сроки, команды строительства/дорог, идемпотентность, команды с причинами отказа, сохранение отчётов, транзакционные инварианты.

**Готово, когда:** серверная модель экономики совпадает с клиентским снимком; повторная команда не дублирует эффект; рестарт не теряет сроки; каждый отказ понятен игроку; доменные сценарии покрыты unit + integration tests.

### Фаза 3. Техническая платформа и производительность

CI, observability, политика хранения, индексы БД, индекс адресных сокетов, backpressure, нагрузочные сценарии, профилирование Pixi/React, контроль бандла и ассетов.

**Готово, когда:** PR не проходит без обязательных проверок; есть воспроизводимые load-test отчёты; заявленная вместимость подтверждена p95/p99, CPU, heap, DB pool и latency.

### Фаза 4. Поселение и прогресс

Каталог зданий как единственный источник данных → ресурсы/склад/производство → уровни и стоимость → строительные очереди/ускорители/помощь → исследования и эффекты → отчёты и квесты.

**Готово, когда:** все здания имеют валидные уровни, footprint, стоимость, требования, эффекты, таймеры и UI; все расчёты серверные и протестированы; баланс сверяется с утверждёнными таблицами.

### Фаза 5. Глобальная карта и экспедиции

Мировая карта и территории → узлы ресурсов → разведка → марши и вместимость → возвращение/грабёж/защита → PvE-объекты и контроль территории.

**Готово, когда:** координаты и видимость проверяются сервером; нельзя собирать/атаковать вне правил; прогресс и маршруты переживают рестарт; отчёты воспроизводимы.

### Фаза 6. Командиры, армия и бой

Найм/рост командиров → классы и уровни войск → лечение/потери → детерминированная формула боя → симулятор и боевые отчёты → PvP и защита от эксплойтов.

**Готово, когда:** одинаковые входные данные дают одинаковый бой; все модификаторы и потери тестируются; сервер не доверяет клиентским боевым параметрам.

### Фаза 7. Кланы, альянсы и социальные системы

Создание/управление кланом → роли/права → клановые здания/исследования → помощь → чат/модерация → совместные цели и войны.

**Готово, когда:** проверены права на каждое действие; нет доступа к чужому складу/личным данным; чат имеет лимиты, модерацию и защиту от спама.

### Фаза 8. События, монетизация и долгосрочный прогресс

Календарь и сезоны → задания/награды → магазин/подписки → платежная интеграция → возвраты/повторные webhook → антифрод и аудит покупок.

**Готово, когда:** платёжные операции идемпотентны и проверяются сервером; нет выдачи покупки по клиентскому сигналу; экономика остаётся устойчивой и без обязательных покупок.

### Фаза 9. Визуальный продукт и выпуск

Арт-лист и оригинальные ассеты → уникальные здания/герои/ландшафты → анимации и эффекты → единый HUD → мобильная адаптация и desktop → accessibility/i18n → PWA/нативная стратегия → закрытая альфа и нагрузочная бета.

**Готово, когда:** интерфейс работает на реальных устройствах, есть fallback, нет критичных ошибок/утечек, производительность измерена, onboarding понятен, релизная документация и поддержка готовы.

## 6. Правила аудита и внесения изменений

Для каждого дефекта вести карточку:
- ID, приоритет, область, файл/строка и точное доказательство;
- влияние на игрока, данные, безопасность или эксплуатацию;
- воспроизводимый сценарий;
- минимальный тест, который сначала демонстрирует проблему;
- исправление и затронутые контракты/миграции;
- повторный тест, регрессия, статус и commit SHA.

### Definition of Done для каждого изменения

- [ ] Код соответствует границам пакетов и текущему стилю архитектуры.
- [ ] Входные данные валидируются; права, мир, владелец и лимиты проверяются сервером.
- [ ] Есть unit/integration/regression test на позитивный и негативный сценарии.
- [ ] Проверены гонки, повтор команды и поведение после рестарта, если затрагиваются состояние/таймеры.
- [ ] `pnpm typecheck`, `pnpm test`, `pnpm check`, `pnpm build` проходят.
- [ ] UI проверен на узком и широком экране, touch и клавиатуре, ru/en.
- [ ] Документация и `STATUS.md` обновлены.
- [ ] Коммит содержит только относящиеся к задаче файлы; push — в рабочую ветку, без force push.
- [ ] В сообщении владельцу указаны commit, тесты, путь проверки/развёртывания и что проверить.

Если изменение затрагивает БД: тест на отдельной копии, проверка rollback/forward compatibility, backup/restore и отсутствие потери пользовательских данных.
