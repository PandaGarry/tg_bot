# TDL — протокол совместной разработки несколькими ИИ

> Версия 1.0 · 12.11.2026 · Статус: действует; владелец проекта поручил организовать совместную работу ChatGPT, Cloud и Arena.ai 12.11.2026.

## 1. Зачем это нужно

Cloud, Arena.ai и ChatGPT работают как одна распределённая команда. У них нет общей памяти чатов и нет гарантированной прямой связи друг с другом. **GitHub — единственная общая память, очередь задач и журнал передачи работы.** Сообщения в чатах — только транспорт для ссылок на конкретные файлы, ветки, PR и задачи.

Ни один агент не должен считать, что другой агент «в курсе» контекста, если это не записано в репозитории.

## 2. Источники истины и порядок приоритета

При конфликте документов агент не выбирает удобную ему версию, а останавливает спорное действие и сообщает о конфликте.

1. Решения владельца проекта в актуальном `docs/DECISIONS.md`.
2. Утверждённая продуктовая спецификация `docs/TDL_PRODUCT_VISION_AND_ACCEPTANCE.md`.
3. Оперативный план `PROJECT_MASTER.md`.
4. Технические контракты и спецификации соответствующей подсистемы.
5. Текущий снимок `docs/AI_COLLABORATION/STATUS.md`.
6. Исторические документы, архивы, старые комментарии и переписка.

Документ с более низким приоритетом не может отменить решение из документа с более высоким приоритетом. Статус «реализовано» допустим только при наличии кода; «проверено» — только при наличии воспроизводимого доказательства.

## 3. Роли

Роли задают ответственность, а не ограничивают возможности моделей.

| Участник | Основная ответственность | Что сдаёт |
|---|---|---|
| **ChatGPT — координатор и интегратор** | Разбивает цели на проверяемые задачи, поддерживает документацию и очередь, готовит задания, проверяет архитектуру/диффы/тесты, принимает handoff, сводит результаты | ТЗ, критерии приёмки, review, интеграционные изменения, обновлённый статус и ссылки на доказательства |
| **Cloud — независимый архитектор и reviewer** | Второе мнение по архитектуре, независимый аудит требований и диффов, поиск рисков, анализ вариантов технологий/ассетов, проверка полноты ТЗ | Краткий review с фактами, ссылками на файлы/строки, рисками и конкретными рекомендациями; отдельный PR, если задача назначена на реализацию |
| **Arena.ai — исполнитель и среда практической проверки** | Работа с репозиторием, запуск приложения в браузере, проверка реального поведения, исследовательские прототипы, в том числе отдельная проверка Godot/Web-экспорта при наличии задачи | Код в собственной ветке, команды и результаты тестов, реальные скриншоты/видео, сведения об окружении и ограничения |
| **Владелец проекта** | Приоритеты, художественные/продуктовые решения, спорные компромиссы и окончательная приёмка | Явное решение или замечания |

Любой агент может предложить улучшение, но не может самовольно менять утверждённую продуктовую цель, экономику, серверный контракт, схему БД или целевой движок.

## 4. Правила веток и изменений

- `main` — интеграционная стабильная ветка, а не рабочая папка агента.
- Каждый исполнитель работает в отдельной ветке: `agent/<TASK-ID>/<short-name>`.
- Один владелец задачи и один набор изменяемых файлов на задачу. Не редактировать один и тот же файл параллельно.
- Перед началом: обновить базовую ветку, прочитать `AGENTS.md`, этот протокол, `PROJECT_MASTER.md`, актуальный статус и handoff своей задачи.
- Запрещены force-push, прямые коммиты в `main`, массовый форматинг/перестройка без задачи, секреты и локальные env-файлы в Git.
- Результат передаётся через PR в `main` (или отдельную интеграционную ветку, если задача зависит от незавершённого PR). PR должен содержать ID задачи, scope, тесты, доказательства, риски и документационные изменения.
- PR не сливается только потому, что агент написал «готово». Нужны review, зелёные обязательные проверки и выполненные критерии приёмки.
- После merge обновляются `PROJECT_MASTER.md`, `docs/AI_COLLABORATION/STATUS.md`, очередь и профильные документы. Только после этого задача считается доступной следующему агенту как интегрированная база.

## 5. Жизненный цикл задачи

`BACKLOG → READY → IN_PROGRESS → REVIEW → ACCEPTED → MERGED → VERIFIED`

1. **BACKLOG:** идея/находка без обещания реализации.
2. **READY:** есть владелец, точный scope, базовая ветка, критерии и запреты.
3. **IN_PROGRESS:** исполнитель работает в своей ветке.
4. **REVIEW:** PR открыт, CI и независимая проверка выполняются.
5. **ACCEPTED:** критерии выполнены; владелец подтвердил продуктовые/визуальные решения, если они требовались.
6. **MERGED:** PR действительно слит в целевую ветку.
7. **VERIFIED:** результат проверен на интегрированной базе; статус и доказательства обновлены.

Нельзя перескакивать через статусы. Закрытая задача не означает, что вся подсистема готова.

## 6. Формат передачи работы

Каждая задача имеет файл `docs/AI_COLLABORATION/handoffs/<TASK-ID>.md` на основе `TASK_TEMPLATE.md`. В нём обязательно указать:

- цель и измеримый результат;
- что читать и от какого commit SHA начинать;
- разрешённые и запрещённые файлы/области;
- точные критерии приёмки;
- команды тестов и ожидаемые доказательства;
- что уже сделано, что не сделано, известные риски;
- кто следующий владелец и что именно ему нужно сделать.

После завершения исполнитель добавляет в handoff итог: PR, commit SHA, изменённые файлы, тесты с фактическим результатом, ссылки на реальные скриншоты/артефакты, остаточные риски и следующий шаг.

## 7. Доказательства и честность статусов

- «Запустил» означает, что процесс реально запущен в названной среде.
- «Проверил в браузере» означает, что пройден конкретный сценарий в браузере; указать commit SHA, viewport, шаги и результат.
- Скриншоты должны быть сделаны из фактического приложения/прототипа. Концепт, рендер или AI-картинка не выдаются за runtime игры.
- «CI зелёный» — только для конкретного run ID и HEAD SHA.
- «Работает на мобильном» — только после теста на согласованном устройстве или эмуляции с указанием ограничений. Desktop screenshot не подтверждает мобильную адаптацию.
- Если проверить невозможно, писать «не проверено» и объяснять почему.

## 8. Как проверяем визуальную часть и 3D-технологию

Цель утверждена: Premium stylized realism, полноценный 3D-мир с изометрической камерой, мобильные устройства и браузер/ПК. Но целевой движок и путь интеграции ещё не утверждены.

Запрещено начинать массовую миграцию PixiJS-клиента или переписывание игры на Godot/другой движок без отдельного сравнительного прототипа и решения владельца. Сначала проверить небольшой одинаковый сценарий на реальных целевых платформах: загрузка сцены, камера, земля, Цитадель и несколько зданий, выбор/размещение, UI-overlay, адаптация viewport, производительность и размер загрузки. Рассмотреть как минимум существующий веб-стек с 3D-рендерером и Godot Web export; сравнивать не по вкусу, а по измеримым критериям из продуктовой спецификации.

## 9. Безопасность и границы

- Не передавать между агентами пароли, токены, содержимое `.env`, персональные данные и production credentials.
- Не запускать destructive DB-команды вне специально созданной тестовой базы.
- Изменения ядра, протокола, схемы БД, экономики, платежей, монетизации, авторизации и production-инфраструктуры требуют отдельного явного разрешения и профильного review.
- Лицензия и происхождение каждого внешнего ассета фиксируются до включения в продукт.
- Не устанавливать зависимости и движки в production-проект ради одноразового теста; прототип изолировать.

## 10. Старт каждого агента

Перед работой агент обязан прочитать:

1. `AGENTS.md`
2. `docs/AI_COLLABORATION/README.md`
3. `docs/AI_COLLABORATION/STATUS.md`
4. `PROJECT_MASTER.md`
5. `docs/DECISIONS.md`
6. `docs/TDL_PRODUCT_VISION_AND_ACCEPTANCE.md`
7. handoff конкретной задачи.

Если документ отсутствует в текущей ветке, не выдумывать его содержимое: сообщить об этом и запросить интегрированную базу.
