# 23 · Двор как конструктор: как сцена главного экрана устроена в клиенте

Круг 7 (27.09.2026). Ответ на вопрос заказчика «как это вшить в игру и как оно должно работать и отображаться».
Это не картинка, а **работающий прототип**: [ui/court/index.html](ui/court/index.html) (`court.js`, `court.css`),
снимки состояний — [ui/court/court-sheet.jpg](ui/court/court-sheet.jpg). Он заменяет подход кругов 3–6, где двор был
одной нарисованной подложкой: подложка годилась, чтобы утвердить стиль и раскладку HUD, но в игре так нельзя —
у каждого игрока свой двор.

## 0. Что заказчик просил и как это сделано

| Требование | Как сделано в прототипе |
|---|---|
| Фон разделить на день и ночь; днём ни фонари, ни окна не горят | Земля — два файла: `ground-day.jpg` и `ground-night.jpg` (на пустой площадке огней нет вовсе). У **каждого здания два спрайта**: дневной (окна тёмные, факелов нет) и ночной (окна и фонари горят, тёплые пятна на снегу). Переключает одно свойство `night`, картинки подменяются |
| Показать главный экран без строений | `?state=empty` — пустая площадка, снимки `court-empty-day.jpg` / `court-empty-night.jpg`. `?state=day1` — только Двор, единственное, что есть с начала |
| Каждое строение — отдельный элемент: передвинуть, перетащить, выбрать место | Каждое здание — свой PNG с прозрачностью, вырезанный с хромакея, стоит на своих клетках (след 2×2, 3×2, 3×3). В стройке здания тянутся пальцем; в обычном режиме — тап → «Переставить». Новое здание: карточка «Поставить» → призрак → тянем → ✓ |
| Свободная камера | Перетаскивание пустого места — панорама, колесо/щипок — зум ×0,85…×2,2, двойной тап — приближение. Границы — край площадки с лесом. Спрайты в 600 px, при зуме остаются чёткими |
| Режим стройки удобный, камера «выше», клетки удобные | См. §5: в 2D камеру нельзя наклонить, зато в ортографической сетке **все клетки одинаковые на всём экране** — и дальние, и ближние. Стройка = отъезд камеры, чтобы вся площадка была в свободной от панелей зоне, + сетка + следы + подсветка. Перспективная сетка круга 5 (трапеция, дальние клетки мелкие) была ошибкой — снята |

## 1. Принцип: сцена — это данные плюс слои

Сервер хранит состояние двора; клиент из него **собирает картинку** каждый кадр. Ничего заранее нарисованного
«целиком» нет.

```jsonc
// состояние двора игрока (сервер → клиент)
{
  "size": 14,                           // клеток по стороне
  "look": { "season": "winter", "time": "night" },   // пора года — из календаря (11-calendar), время — см. §6
  "wall": { "level": 3 },               // частокол — тоже здание, стадии по уровню (следующий шаг, §9)
  "buildings": [
    { "id": "keep",     "type": "keep",    "level": 7, "x": 3, "y": 3 },
    { "id": "sawmill1", "type": "sawmill", "level": 6, "x": 7, "y": 2, "pin": "collect" },
    { "id": "wh1",      "type": "warehouse", "level": 1, "x": 7, "y": 6, "building": { "until": 1790000000 } }
  ]
}
```

Действия игрока — три команды: `place(type, x, y)`, `move(id, x, y)`, `upgrade(id)`. Клиент проверяет их
локально ради отзывчивости (границы, пересечения, стоимость), сервер — окончательно, и присылает новое состояние.
Каталог зданий (`TYPES` в `court.js`: имя, след, спрайты, точка опоры) — общий справочник; в игре он лежит рядом
с таблицами [09-numbers.md](09-numbers.md).

Слои снизу вверх (все, кроме HUD, живут в одном контейнере, которым двигает камера):

1. **Земля** — картинка площадки с окрестностями по поре года и времени суток (сейчас 2 файла: зима день/ночь).
2. **Сетка** (только в стройке) — SVG-линии по углам клеток; двухцветные, чтобы читаться и на снегу, и на земле.
3. **Следы** — ромбы занятых клеток (в стройке), зелёный/красный след призрака.
4. **Здания** — спрайты, отсортированные по глубине; у каждого дневная и ночная картинка.
5. **Призрак** — переставляемое или новое здание, полупрозрачный, с ✓/✕ над ним.
6. **Подписи и пины** — таймер стройки, «забрать», «улучшить»; в прототипе внутри мира, в клиенте лучше в слое экрана.
7. **HUD** — не двигается и не масштабируется с камерой; в прототипе берётся из `hud/main-screen.html` как есть.

## 2. Геометрия: ортографическая диметрия

- Площадка — ромб **14×14 клеток** (196 клеток; Двор 3×3, средние здания 2×2, загон 3×2 — под 11 типов из
  [04-systems.md](04-systems.md) с запасом на 5 пунктов марша и украшения).
- Клетка — ромб `W×H = 71,4×41,4` px мира (≈1,72:1, камера ≈35° над горизонтом — ровно как генератор рисует
  «диметрию», и как выглядит нынешняя подложка). Ось *x* идёт по экрану вправо-вниз, *y* — влево-вниз.
- Угол клетки `(i, j)` → мир: `sx = TOPx + (i − j)·W/2`, `sy = TOPy + (i + j)·H/2`.
  Обратно (палец → клетка): `u = (wx − TOPx)/(W/2)`, `v = (wy − TOPy)/(H/2)`, `i = (u+v)/2`, `j = (v−u)/2`, потом `floor`.
- След здания `(x, y, fw, fh)` — четыре угла `(x,y) (x+fw,y) (x+fw,y+fh) (x,y+fh)`; **нижний угол** `(x+fw, y+fh)` —
  точка опоры спрайта.
- Спрайт масштабируется так, чтобы ширина его подошвы (`patch`, px) стала шириной следа `(fw+fh)·W/2`, и ставится
  нижним углом подошвы (`tip`, px спрайта) на нижний угол следа. Поэтому один и тот же спрайт встаёт в любую клетку
  одинаково — это и есть причина уйти от перспективной подложки.
- Порядок отрисовки — по сумме координат нижнего угла следа (`x+fw+y+fh`): что ниже по экрану, то ближе к камере
  и рисуется позже. Для равных сумм — по `x+fw`. На прямоугольных следах этого хватает; если появятся длинные
  здания (стена), нужна топологическая сортировка «A позади B, если A.x+fw ≤ B.x или A.y+fh ≤ B.y».

## 3. Камера

- Весь мир — один контейнер с `transform: translate(tx, ty) scale(z)`; земля, сетка и спрайты внутри, HUD снаружи.
- Панорама: перетаскивание пустого места; зум: колесо, щипок двумя пальцами (вокруг середины между пальцами),
  двойной тап (×1,5). Пределы `z ∈ [0,85; 2,2]`; сдвиг ограничен так, чтобы за краем земли не было пустоты
  (при `z < 1` мир может «плавать» между краями — это нужно стройке).
- Обычный режим: `z = 1`, площадка целиком в кадре с лесом вокруг — тот же кадр, что на подложке круга 5.
- Стройка: `lookAt(центр площадки → точка экрана (740, 318), z = 0,86)` — площадка целиком в зоне, свободной
  от вкладок слева и карточек снизу; фон за краем — размытая земля.
- Первый день: камера может стартовать ближе (`z ≈ 1,2`), пустой двор вблизи выглядит уютнее, чем с высоты.

## 4. Стройка и перестановка: сценарии

| Шаг | Что видит игрок |
|---|---|
| Кнопка «Строить» | Камера отъезжает, сетка и следы включаются, HUD прячет всё лишнее, снизу карточки по вкладкам Хозяйство · Война · Наука · Украшения |
| «Поставить» на карточке | Призрак здания появляется на ближайших свободных клетках у центра экрана, над ним ✓ и ✕; след зелёный |
| Тянем призрак | Клетка считается из положения пальца минус смещение, с которым его схватили — здание не прыгает под палец. Красный след и краснеющий спрайт — место занято или за краем, ✓ погашена |
| ✓ | Здание встаёт в состоянии «стройка»: спрайт лесов (`d-03`) по размеру следа, подпись «Склад · 12:40» с полоской; занят строитель. По окончании — спрайт здания 1-й стадии |
| Готовое здание в стройке | Схватил — оно стало призраком (на старом месте остаётся бледная копия), тянем, ✓ или ✕ |
| Обычный режим, тап по зданию | Подсветка и пузырь «Улучшить · Переставить · Инфо»; «Переставить» — тот же призрак без входа в режим стройки |
| Тап по пустому месту | Снять выбор |

Счётчик «свободных клеток» в заголовке стройки считается из следов. В игре к проверке добавятся: лимит зданий типа
(«1 / 2»), уровень Двора (карточка с замком), ресурсы и очередь строителя.

## 5. Почему в стройке камера не «поднимается», и почему это правильно

В RoK камера наклоняется в стройке, потому что RoK — 3D. У нас 2D-спрайты: у каждого здания один ракурс, наклонить
камеру нельзя, не перерисовав всё. Но цель наклона — не сам наклон, а **удобство расстановки**: видеть всю площадку,
одинаково крупные клетки, понятные следы. В ортографической сетке это выполнено по построению: клетка в дальнем углу
такая же, как в ближнем, здания не загораживают клетки за собой сильнее, чем в RoK. В круге 5 сетка была
перспективной трапецией с мелкими дальними клетками — вот что делало стройку неудобной; теперь она снята.

Варианты, если всё же захочется «вид сверху» в стройке:

- **Второй набор спрайтов «сверху»** (90°) для стройки — удвоение ассетов ради одного режима; не советую.
- **3D-двор** (Three.js/Babylon, модели вместо спрайтов) — камера наклоняется как угодно, свет/время суток
  бесплатны, но в 3–4 раза дороже в производстве и тяжелее для слабых телефонов.
- **Оставить как есть**: ортографический ракурс ≈35°, стройка = отъезд + сетка. Так живут Clash of Clans, Hay Day,
  Boom Beach, Forge of Empires — самые массовые 2D-строилки. **Рекомендую этот вариант.**

## 6. День и ночь

- Сейчас: два набора картинок (земля ×2, каждое здание ×2). Переключение — одно свойство; в клиенте переход делать
  кроссфейдом (обе картинки в слое, анимируется прозрачность, 1–2 с).
- По чьим часам: **устройства игрока**, чтобы за окном и на экране было одно время; серверные «часы мира» остаются
  для календаря. Порог: день 7:00–18:00, зимой темнеет раньше (таблица по порам года). В настройках — «как за окном /
  всегда день / всегда ночь».
- Дальше, чтобы не удваивать все ассеты при 5 стадиях: ночь = дневной спрайт × синяя градация + отдельный «слой огней»
  (только окна и фонари). Это уменьшит ночной набор с полной копии до маленьких масок. В прототипе не делал: заказчик
  просил именно раздельные день/ночь — они есть; переход на слой огней — оптимизация этапа C.

## 7. Поры года

Земля — по одному файлу на пору и время (зима день/ночь есть; весна, лето, осень — по тому же рецепту «та же площадка,
другой сезон», как делались концепты круга 6). Здания — два набора: «в снегу» и «без снега» (весна/лето/осень
отличаются землёй и лесом, не крышами). Пора включается модулем календаря ([11-calendar.md](11-calendar.md), единица
`look` ставит признак на корень разметки) — сцена читает `season` из состояния и подставляет файлы.

## 8. Ассеты: как сделаны и как делать дальше

1. Генерация **листа** на пурпурном фоне (#FF00FF): 3 здания в ряд, одна камера, дневной свет, референс стиля —
   подложка круга 5. Затем правка того же листа «ночь: окна и фонари горят, фон не трогать» — геометрия сохраняется
   пиксель в пиксель, поэтому дневной и ночной спрайт совпадают по подошве.
2. Нарезка: `pnpm icons court/sprites/sheet-a.png --prefix a --pad 4 --merge-gap -1` — хромакей, связные пятна,
   PNG с прозрачностью; в этом круге в резак добавлены `--merge-gap -1` (не склеивать соседние рамки — на листах зданий
   они перекрываются по диагонали) и маска «только своё пятно + 2 px края» (в рамку попадали куски соседей).
3. В каталог записываются `patch` (ширина подошвы) и `tip` (нижний угол подошвы) — пока вручную по листу; следующий
   шаг — резак сам находит подошву (самая широкая строка пятна) и пишет `sprites.json`.
4. Правило стиля: новые здания — **правкой существующего листа** («замени средний дом на кузницу»), не с нуля; так стиль
   не расползается.

Сделано в круге 7: 11 спрайтов × день/ночь (Двор, Лесопилка, Каменоломня, Ферма, Загон, Склад, Казарма, Лазарет, Пункт
марша, Паутина, Стройка) + земля день/ночь. Это стадия I–II зданий; стадии III–V — по тому же конвейеру (см. 22-й
документ, §5 и §7).

## 9. Чего в прототипе ещё нет (по порядку)

1. **Стена (частокол)** как здание: периметр из повторяемых секций (прямая ×2 направления, угол, ворота, башня),
   5 стадий; в игре это здание «Стена» из 04-systems.
2. **Тропинки** от ворот к зданиям — автоматически по занятым клеткам (слой между землёй и зданиями).
3. **Люди и животные** вне загона, дым, флаги — немного анимированных спрайтов; количество растёт с двором.
4. **Стадии III–V** зданий и весна/лето/осень.
5. **Слой огней** вместо полных ночных копий (оптимизация ассетов).
6. **Подписи в слое экрана** (сейчас масштабируются вместе с миром), длинное нажатие для перестановки без пузыря.
7. **Рендерер**: прототип на DOM — до ~50 спрайтов хватает; с анимацией и частицами переходить на Canvas/WebGL
   (PixiJS), атласы, webp, догрузка только текущей поры и нужных стадий.
