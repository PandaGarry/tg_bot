| Вопрос | Решение |

| Место в плане | внутри шага 1 (ядро), до закрытия шага и до модулей шагов 4–7 |

Следствие из четырёх модулей пор года: полоса (`lane`) живёт **на мир, а не внутри модуля**. Ядро держит инвариант «в полосе `season`
ровно одна включённая единица» через все модули сборки: включили зиму — весна гаснет тем же действием. Проверка сборки это
подтверждает, а не надеется на порядок вызовов.

## Зачем

Сегодня у модуля одно состояние на мир: `enabled` или `disabled`. Этого мало для трёх разных задач:

- **основные механики** (двор, карта, сбор, марш, бой, столица, клан) должны стоять на месте и не гаснуть от чужой воли;
- **временные события** и **праздники** должны включаться и выключаться сами, по календарю, с пробелами;
- **поры года** должны меняться по датам, тянуть за собой вид игры и держать ровно одну пору включённой;
- **точечно** нужно уметь гасить не «систему», а одну механику внутри неё.

## 1. Три вида модулей

| Вид | Что это | Кто переключает | Пример |
|---|---|---|---|
| `core` | основные: механики жанра | только сервисное выключение с причиной и карантин; сам себя — никогда | двор, карта, сбор, марш, бой, столица, клан |
| `timed` | временные: повременные события и мировые праздники | ядро по расписанию, оператор вручную | полнолуние, урожай, Новый год, Хеллоуин, 8 марта |
| `seasonal` | сезонные: поры года | ядро по расписанию, оператор вручную | четыре модуля: `season-spring`, `season-summer`, `season-autumn`, `season-winter` |

**Терминология.** Слово «сезон» уже занято — в [07-modules.md](07-modules.md) «сезон события» значит «модуль не удаляем,
а гасим и включаем снова». Чтобы имена не путались:

- `seasonal` в коде и документах — **пора года** (весна, лето, осень, зима);
- сезон события остаётся сезоном события.

Ключ `kind` обязателен у каждого модуля. Реестр падает, если его нет: модуль без вида — незаконченное решение, а не мелочь.

## 2. Единица (unit) — точечный выключатель

Модуль — это каталог кода, таблицы и миграции. **Переключается единица внутри модуля.** Модуль целиком гасится только
карантином и сервисным выключением, для точечной работы есть единицы.

```ts
defineModule({
  id: "events",                     // каталог
  kind: "timed",
  version: 1,
  units: [
    { id: "harvest-week", role: "event", titleKey: "events.harvest.title", lane: "holiday",
      window: { repeat: { kind: "yearly", month: 9, day: 20 }, at: "12:00", lengthMs: 7 * DAY } },
    { id: "halloween", role: "event", titleKey: "events.halloween.title", lane: "holiday",
      window: { repeat: { kind: "yearly", month: 10, day: 25 }, at: "12:00", lengthMs: 7 * DAY } },
    { id: "full-moon", role: "event", titleKey: "events.fullMood.title",
      rotation: { lane: "daily", weight: 3, cooldownDays: 10 } },
  ],
  // Команда сама говорит, чья она: чужой единицы в модуле не бывает.
  server: { commands: [{ unit: "harvest-week", id: "events.harvest.claim", ... }] },
});
```

```ts
export interface UnitDecl {
  id: UnitId;                       // «quarry», «halloween», «winter»
  role: "mechanic" | "event" | "season" | "look" | "pass";
  titleKey: string;                 // имя для панели: ключ словаря, не строка
  defaultState?: ModuleState;       // на новом мире; у событий и пор года — disabled
  lane?: LaneId;                    // полоса: «ровно один включённый» и «не чаще, чем…»
  window?: WindowDecl;              // точные даты: праздники, поры года
  rotation?: RotationDecl;          // пул повседневных событий: выбор по дате
}
```

Правила, которые ядро держит само:

| Правило | Как звучит |
|---|---|
| Принадлежность | каждая команда, выгода, гнёздо вида и срок принадлежат ровно одной единице; реестр падает на чужой |
| Эффективное состояние | единица работает, если включён и модуль, и единица |
| Полоса `season` | в полосе пор года ровно одна включённая единица — ни двух, ни ни одной; полоса общая на всю сборку, поэтому четыре модуля пор года не могут встать вдвоём |
| Полоса `holiday` | не больше одной включённой единицы в полосе; полосы общие на сборку, а не на модуль |
| Отказ | команда выключенной единицы получает `kernel.unit.disabled` со своим текстом, а не общее «нельзя» |
| Модификаторы | выгоды выключенной единицы в расчёт не входят — как сегодня у выключенного модуля |
| Вид | гнёзда выключенной единицы не заполняются: экран механики пропадает вместе с механикой |

Единица нужна не «на будущее», а сразу: двор — это `quarry`, `sawmill`, `farm`, `warehouse`; их можно гасить по одному,
не трогая остальных. У каждого модуля поры года свои единицы внутри: `look` (вид игры) и, если нужно, `mechanics`.

Свет/вид поры года: единица `look` включённого модуля поры ставит признак на корень разметки; палитра меняется
переменными стиля, без перезагрузки кода и без пересборки клиента. Вид есть у каждой поры в её собственном модуле,
поэтому «весенний вид» уходит в архив вместе с весной, а не остаётся мёртвой веткой в общем модуле.

## 3. Расписание: точные даты и пул

Правило «модуль не запускает себя» остаётся. Расписание — **объявление, а не код**: модуль описывает окна, ядро считает
план, ставит сроки на старт и на конец, включает и выключает. Никакого `setInterval` в модуле по-прежнему нет.

Два способа задать окно:

| Способ | Для чего | Как задаётся |
|---|---|---|
| `window` | праздники и поры года: известны точные дата и время | `repeat` (ежегодно/ежемесячно/еженедельно/разово), `at` (час и минута), `lengthMs` |
| `rotation` | повседневные события: пул, из которого в день идёт одно | `lane`, `weight`, `cooldownDays`, `months`/`season` — привязка к месяцу и поре года |

`rotation` — детерминированный выбор по дате (seed = дата + пора года), поэтому **план можно напечатать заранее** и он
совпадёт с тем, что случится. Это и есть ответ на «события меняются по сезонности и месяцу»: весной в пуле одни события,
осенью другие, вес задаётся объявлением, а не случайностью процесса.

Пробелы и перегруз:

| Правило | Смысл |
|---|---|
| Одно окно в полосе | в полосе `holiday` не больше одного окна за раз |
| Пробел между окнами | `minGapMs` между окнами одной полосы; выходит меньше — окно сдвигается вперёд, не назад |
| Кулдаун повторов | одна и та же единица в `rotation` не выпадает чаще, чем `cooldownDays` |
| Потолок месяца | `maxPerMonth` окон полосы за месяц: праздник не наслаивается на праздник |
| Пустой день | день без окон — законный день; календарь на 90 дней видно заранее |

Что показываем и когда проверяем:

- `pnpm schedule --days 90` — план из ядра тем же расчётом: окна, полосы, пробелы, пропуски. Один взгляд — и видно, что перегруза нет.
- `pnpm check` ловит сломанное расписание на сборке: неверная дата (29 февраля), нулевая длительность, две поры года на один день, переполнение полосы.
- `/api/schedule?days=90` — то же для оператора на боевом мире.

Двое часов, и это важно не путать:

- **календарь (время сервера)** — настоящее: по нему идут окна событий, сроки оператора и карантин.
  Событие, назначенное на 1 марта, идёт 1 марта, даже если мир перед этим лежал сутки;
- **ход мира** — игровой: по нему идут сроки игроков (марш, стройка, сбор). Он стоит, пока процесс
  не работает, поэтому оставшиеся минуты на простое не сгорают (см. `08-ops.md`).

Простой мира и пропущенное окно (окна считаются по календарю, поэтому промежуток простоя — настоящий):

| Вид окна | Мир стоял, окно началось и ещё идёт | Окно прошло целиком мимо |
|---|---|---|
| `window` (праздник) | догоняем: окно продолжается, `schedule.resume` | пропуск, `schedule.skipped`, причина `downtime.ended` |
| `season` (пора года) | догоняем: пора продолжается, `schedule.resume` | следующий день решает по календарю |
| `rotation` (повседневное) | не догоняем, но и не теряем: окно просто продолжается, `schedule.continue` | пропуск, причина `downtime.rotation`: вчерашнего дня не бывает |
| модуль закрыт | окно молчит, пока его не вернут: пропуск, причина `module.off` | то же |

Пропусков за долгий простой бывают сотни, поэтому в журнал идёт **итог на единицу** (`unit`, `lane`, `count`,
`reason`, `firstKey`, `lastKey`), а точные ключи — в ответе и в счётчиках. Сумма `count` всегда равна
счётчику `scheduleMissed`: ничего не теряется и ничего не считается дважды.

Ключ окна — `<unit>:<начало окна>`. Он не даёт запустить окно дважды после перезапуска и не даёт дважды выдать награду.

## 4. Кто и как переключает

| Способ | Кто | Обязательные условия | Журнал |
|---|---|---|---|
| Расписание | ядро | план из объявлений; ключ окна | `schedule.start`, `schedule.stop`, `schedule.skipped` |
| Сервисное выключение | оператор (`ADMIN_TOKEN`) | **причина** и **срок возврата** `until`; для `core` — только так | `access` + `admin.switch`, по сроку `module.service.restored` |
| Карантин | ядро само | 3 отказа подряд за 60 с или обработчик дольше 250 мс | `unit.strike`, `unit.quarantine`, `unit.quarantine.release` |
| Сборка | тот, кто выпускает код | `MODULES_DISABLED` на старте процесса: в сборке есть, в мире не поднимается | `boot.modules` |

Ответ на «не выключать основные без необходимости»:

- сама механика себя выключить не может, и никто не может выключить чужую единицу;
- гасить `core` в игре нельзя: нет команды, нет кнопки, путь — только ключ оператора;
- **сервисное выключение требует причину и срок**: «выключил для теста и забыл» невозможно, ядро вернёт само;
- по сроку модуль возвращается **в своё рождённое состояние**: большое событие месяца, рождённое закрытым,
  после временного включения снова закрыто и ждёт своего шага плана — временная воля оператора не делает его вечным;
- выключенная механика не теряет данные: её сроки не берутся, работа замирает и продолжается после возврата — марш не пропадает, а ждёт;
- **карантин — не наказание, а лечение**: сбойная единица уходит с расчёта на 60 с, ядро пробует вернуть её само, с отступом 60 с → 5 мин → 30 мин; после третьей неудачи зовёт оператора. Мир при этом жив.

Ручной запуск поры года и праздника оператором — поверх расписания: `POST /api/modules { id, unitId, state: "enabled", until, reason }`.

**Примерка поры года** (утверждена заказчиком 25.09.2026). Пришло время зимы, и её надо готовить заранее: оператор
включает `season-winter.winter` — и мир живёт зимой, хотя на календаре осень. Что при этом происходит:

- включённая пора и её вид (`look`) работают: вид идёт за порой, а не решает сам;
- соседи в полосе `season` **уступают** (причина `yielded`, в панели видно `yieldedTo`): две поры года разом мир не
  показывает, но вернуть управление можно в любой миг — снятие примерки возвращает календарь;
- **содержимое повседневных окон берётся по примеряемой поре**: зимой выпадают зимние дни, а не осенние;
- в журнал идёт `schedule.rehearsal`, а в `/api/health` — `seasonRehearsal`: видно, что мир живёт не по календарю;
- примерка идёт **с начала текущих суток** (иначе окно дня, начавшееся утром, осталось бы от прежней поры) и живёт
  ровно своим сроком `until`; без срока — одна пора (92 дня), дальше снова решает календарь.

Календарь при этом не переписывается: праздники, недели и дни живут по своим датам, а сезон меняется **только**
на время примерки. Так и задумано: «включил зиму в ноябре» больше не ломает год, потому что ломать нечего — есть воля
оператора со сроком и календарь, который ждёт своего дня.

**Как снять примерку.** `POST /api/modules { id, unitId, state: "auto" }` — «вернуть календарю». Запись оператора
стирается целиком (и срок, и причина), дальше решает календарь. Обычное `state: "disabled"` — это **воля оператора**:
она сильнее календаря, живёт до своего срока, а без срока — до отмены. Разница важна: выключив примерку обычным
`disabled`, вы запретите зиме наступить 1 декабря; снимайте примерку через `auto`.

**Уступка — только у того, кому есть что уступать.** Сосед в полосе зовётся `yielded`, только если без перебивки он был
бы включён (идёт его окно, в силе его собственная воля или он всегда включён). Лето зимой — это законный отдых
(`between-windows`), а не уступка, и панель так и говорит.

Что это даёт при подготовке сезона: в параллельном мире (см. `08-ops.md`) включите нужную пору и проверяйте содержимое
и вид; когда всё готово — доработка уходит в основной мир, и там сезон наступит по календарю сам.

## 5. Защита: ошибки, падения, мусор

| Угроза | Защита |
|---|---|
| Обработчик бросил исключение | команда получает отказ, журнал `sim.command.error` с единицей и id команды; стек не уходит игроку |
| Обработчик повис | сторож 250 мс: отказ команды, журнал `sim.command.slow`, карантин единицы |
| Модуль врёт в эффекте: NaN, минус, чужой ресурс, больше предела | каждый эффект проверяется до применения; отказ всей команды, транзакция откатывается, журнал `security.effect` |
| Кривые строки в своих таблицах | снимок проверяется схемой (zod), объявленной модулем; мусор → снимок по умолчанию + карантин единицы, а не кривой экран |
| Сломанное расписание | `pnpm check`: даты, длительности, полосы, `exactly-one`; ошибка ломает сборку, а не мир |
| Двойное окно | ключ окна; повтор невозможен, как у сроков сегодня |
| Падение процесса | право писателя и `resume` в пульсе: окна догоняются по правилам раздела 3, а сроки игроков переносятся на простой |
| Испорченный пульс | пульс — источник правды о ходе мира; запись из будущего или нулевая не принимается: журнал `pulse.suspect`, часы встают на настоящий миг |
| Забытое выключение | обязательный `until` и авто-возврат |
| Карантин навсегда | отступ растёт, третья неудача требует оператора; состояние и причина видны в `/api/health` |
| Чужая воля | переключение только себе; чужая команда — `kernel.command.forbidden`, след `module.foreign-switch` (уже есть) |

Легирование (то, что видно снаружи, а не только в логе):

```
GET /api/modules →
{

    { "id": "season-autumn", "state": "enabled" },
    { "id": "month-window", "state": "disabled" }

      "role": "season", "lane": "season", "state": "enabled", "reason": "window",
      "window": { "key": "autumn:...", "start": ..., "stop": ... } },
    { "key": "holiday.halloween", "moduleId": "holiday", "unitId": "halloween",

## 6. Что уже есть и что появится

Уже есть и останется: состояния на мир (`module_states`), выключение только себя, отказ чужой команде (`kernel.command.forbidden`),
включение оператором (`ADMIN_TOKEN`, пустой ключ закрывает путь), просроченные сроки после включения проводятся по одному разу,
журналы, проверка контракта при сборке.

Построено и проверено (этот проход, шаг 1):

1. **`kind` у модуля и `units` у единиц** — обязательно, реестр проверяет: вид назван, полосы не спорят, команда принадлежит
   своей единице, «временной» и «сезонный» модуль без единиц — ошибка сборки.
2. **Таблицы переключателей**: `unit_states` (миграция `0002_unit_states.sql`) — ключ `(world_id, module_id, unit_id)`,
   `state`, `until_ms`, `reason`; `module_states` получила `until_ms` и `reason`; `unit_health` (миграция `0003_unit_health.sql`) —
   карантин единицы или модуля, счёт сбоев, отступ лечения, нужда в операторе, последняя ошибка. Живые записи — только там,
   где вмешались оператор или ядро: без записи решает расписание.
3. **Часы расписания**: `window`, `rotation`, полосы, пробелы, ключ окна, разогрев на год назад. Календарь по реальным датам
   (время сервера, UTC+3), работа внутри окна — по часам мира: двое часов названы и разведены (см. раздел 3).
4. **Переключатели единиц** (`unitStates` в ядре): порядок силы «оператор → карантин → модуль → окно → вид модуля», причины
   `operator`, `quarantine`, `module-off`, `module-closed`, `window`, `between-windows`, `always-on`, `core`; у операторской
   перебивки — своя записка (`note`), срок `until` снимает запрет сам, кэш состояний живёт до ближайшего края окна или срока.
5. **Карантин и сторож**: три отказа подряд за 60 с или обработчик дольше 250 мс — единица уходит с расчёта, лечение с отступом
   60 с → 5 мин → 30 мин; четвёртая неудача требует оператора. Сроки единицы на карантине ждут (`deadline.postponed`)
   и догоняют ход после возврата, включение снимает карантин и с единицы, и с модуля. Волны живут час: сбойный код не лечится
   бесконечно. Журналы `unit.strike`, `unit.quarantine`, `unit.quarantine.release` (с меткой `by: time|operator`).
6. **Догон после простоя**: `schedule.resume`, `schedule.continue`, `schedule.skipped` по правилам раздела 3; окна, кончившиеся
   за простой, считаются отдельным расчётом по промежутку (в плане от настоящего мига их уже нет); счётчики `scheduleResumed`,
   `scheduleContinued`, `scheduleMissed`; перезапуск не дублирует `schedule.start`.
7. **Часы и пульс**: ход мира считается из пульса (`world.resume` с `downtimeMs`, `worldAt`, `calendarNow`), испорченная запись
   не сдвигает мир назад и не замораживает его (`pulse.suspect`); срок возврата возвращает модуль в рождённое состояние.
8. **Ручки и легенда**: `/api/modules` (модули, единицы, карантины; точечный переключатель с `until` и `reason`),
   `/api/schedule`, `/api/health` с двумя часами и всеми счётчиками; `pnpm schedule --days 90`;
   проверки расписания в `pnpm check` (2026, 2027, 2028: пробелы, наложения, покрытие пор года, «ровно одна пора»).
